Say: "Three conclusions, and they drive the rest of the talk." 1. Reads dominate: ~25k search QPS at peak versus ~12 writes a second. Scale reads horizontally (replicas, caches, CDN); keep the write path simple and correct. 2. Walk it bottom-up, because that's how data moves (about 90 seconds): 1. Sources: 800+ MLS feeds, county public records, third-party data (schools, crime, walkability, demographics). 2. The ingest pipeline (Cloud Run workers, one Cloud Tasks queue per MLS) normalizes everything into one canonical property model and writes the golden record to AlloyDB (next slide). 3. Every committed change goes out on Pub/Sub via a transactional outbox as property.changed, carrying the MLS ModificationTimestamp as its version. 4. Each consumer has its own subscription: the OpenSearch index, Valkey cache purge, a BigQuery subscription for history and ML, and the alert matcher. Every sink checks the version, so redelivery and replay are harmless. 5. Domain services sit above the stores. Mortgage is isolated on purpose: own database, own GCP project and VPC, field-level encryption, audit log (TILA-RESPA, credit data). 6. The gateway/BFF does auth, rate limiting and server-side rendering for SEO (listing pages are a huge share of organic traffic). 7. The CDN fronts everything cacheable: SSR pages with short TTLs, map tiles, all photos. Principle: one write path, many read models. The golden record is the only place a fact is written; everything else is a projection we can rebuild from the raw GCS zone, BigQuery history or a Pub/Sub seek. "Why not microservices for everything": these are domain boundaries owned by teams; split further only where scaling or ownership demands it. Search and alerts scale very differently, so they're separate from day one.

The accuracy loop behind 99.9%

Nightly full-key reconciliation per feed catches missed deletes. Per-feed freshness SLOs, field-level provenance, a review queue for quarantined records.

Lead with: "800 MLSs sounds like 800 integrations. It isn't. Most run on a handful of vendor platforms (CoreLogic Matrix, FBS Flexmls, Black Knight Paragon, Rapattoni…), and the industry is converging on the RESO Web API and Data Dictionary. So we build ~15 platform adapters and treat each MLS as configuration: credentials, cadence, field mappings, quirks." 1. Connect: incremental pulls on a ModificationTimestamp cursor; cadence 1–15 min per MLS. Cloud Scheduler fills one Cloud Tasks queue per MLS, with maxDispatchesPerSecond and maxConcurrentDispatches set to that MLS's contract: a slow MLS can't starve the others, and retries with backoff are built in. Pub/Sub can't rate-limit per source; that's why Tasks is here. Use neutral aggregators (MLS Grid, Trestle) where an MLS distributes through them. 2. Land: untouched payload to GCS (gs://raw/…) with feed, timestamp, cursor. Audit trail and replay button. 3. Normalize: declarative mapping per MLS (versioned, tested in CI against sample payloads). Onboarding an MLS needs no code deploy. 4. Validate: USPS CASS address standardization, geocode, rules (price > 0, plausible sqft, sold after listed). Bad records are quarantined with a reason; the previous good version stays live. 5. Resolve: stable property_id from county FIPS + parcel number (APN), falling back to normalized address + geo proximity. Duplicates across overlapping MLSs merge; per-field precedence and provenance. Accuracy loop: incremental feeds don't reliably report deletes. Nightly, pull all active keys per feed and diff. Per-feed SLO: 95% of changes visible within 5 minutes of the MLS publishing them; alert when a feed goes quiet. Fan-out: Pub/Sub, not Kafka, because we have ~12 events/s; Kafka means brokers and partitions sized for scale we don't have. Not Cloud Tasks either: a task hits one target, so five consumers would mean five tasks and a producer change for every new consumer. Ordering: the version check is the guarantee (write only if the MLS ModificationTimestamp + sequence is newer). Ordering keys only keep publish order; they don't cover worker races, redelivery or replay, and one poison message blocks its key. MLS display rules (IDX/VOW attribution, allowed fields) live in the same per-MLS config and are enforced at render time.

Event rules: transactional outbox to Pub/Sub · MLS timestamp as version, checked at every sink · CloudEvents schemas · dead-letter topics · every read model rebuildable

Say: "There's exactly one place a fact about a property gets written: the golden record in AlloyDB. Everything else is a read model built from the event stream; I can throw any of them away and rebuild it." Why AlloyDB: 200M × ~10 KB ≈ 2 TB, comfortable for Postgres with hash partitioning on property_id. Transactions for upsert + outbox; PostGIS for write-time geometry; read pools for detail reads that miss the cache; a cross-region secondary for DR. ~12 writes/s. Why not Spanner: it sells multi-region writes and 99.999% we don't need at 12 writes/s, and we'd lose PostGIS and plain Postgres tooling. Nothing needs Cassandra. Why not event sourcing everything: the raw GCS zone plus BigQuery history already give replay and history; querying current state from events is painful. The lake keeps every version. Outbox: record + outbox row in one transaction; a small relay publishes to Pub/Sub. No dual-write bugs. Pub/Sub sits behind our own publish/consume adapter with CloudEvents envelopes, so moving to Kafka later is one module. Ordering: consumers apply a version check (MLS timestamp + sequence), so replays, redelivery and duplicates are harmless. Schemas: Protobuf in CloudEvents envelopes, Pub/Sub schemas plus backward-compatibility checks in CI. History: a Pub/Sub BigQuery subscription lands every change with zero pipeline code (Datastream would only mirror current state). BigQuery tables for Apache Iceberg on GCS, partitioned by state and year (deeds, tax assessments, listing history, permits). Time travel lets ML train on what we knew at the time, avoiding leakage. Privacy: CCPA deletions fan out as an event; every store with user data has a deleting consumer. Mortgage/credit data in its own GCP project with Cloud KMS field-level encryption and access logging.

The event-driven showcase (60–90 seconds). Say: "The obvious design re-runs every saved search on a timer. 30M searches every 10 minutes is 50k QPS, more than our entire user search load, and alerts are still 10 minutes stale. So I flip it: index the searches, stream the listings through them." Matcher: on save, the area (polygon, ZIP, city, school district) becomes H3 cells (res 7, ~5 km²; ~40 per search). Postings: cell → search ids, plus compiled filters. A listing is a point in exactly one cell: look up candidates, exact point-in-polygon + filter check. Typical cell: thousands of candidates, <1 ms; densest (Manhattan) ~200k, ~10 ms. Memory: 30M × 40 × 8 B ≈ 10 GB + ~9 GB filters ≈ 20 GB, sharded by coarse H3 parent, 3 replicas. State rebuilds from the saved-search table in AlloyDB plus a GCS snapshot; a crashed node is back in minutes. Classifier: only buyer-relevant changes (new, price drop, back on market, open house). Storm guard: a feed suddenly emitting 5× its normal change rate has its alerts held and on-call paged. Delivery: idempotency key = hash(user, listing, change, version) with SET NX + TTL on a small no-eviction Valkey instance (one less database than Bigtable). One notification even if three searches match. Quiet hours, daily caps, digest overflow. SMS only with TCPA consent; CAN-SPAM unsubscribe. SLO: p95 under 60 s from ingest to device. The MLS poll interval comes before that and is outside our control. Safety net: nightly batch re-runs saved searches over the last 24h of changes; dedupe prevents double sends. Alternative: OpenSearch percolator is a valid v1 "buy"; a custom matcher gives predictable latency and fast rebuilds for our narrow query shape.

Say: "I budget the 200 ms before I design anything. If OpenSearch gets 70 ms, the index must be designed so a query never fans out to every shard and never does expensive geometry. That's the next two slides." - The cache key is the normalized query (sorted filters, rounded price bounds) plus the map tile, not the raw viewport. Raw viewports are unique; tiles are shared. That's what gets the hit rate to ~40%. - Re-rank runs under a deadline; if the request is already slow it's skipped. Users never wait for personalization. - Hydration: the index returns ids plus sort/filter fields; display data comes from Valkey in one MGET. Filter-plus-terms queries on a ~2.5 GB in-memory shard usually run in single-digit to tens of ms; 70 is conservative at p95 under load. p99: internal target ~350 ms, watched but not the SLO.

Search deep dive · Geospatial indexing

Geometry at write time, not search time

Interior cells: term filter.
Boundary cells: exact check.

At write time · 1M a day

  • Store H3 cells at resolutions 5, 7 and 9
  • Point-in-polygon once in PostGIS for district, ZIP, city; store the ids
  • One denormalized ~4 KB doc per listing
  • Index with the listing version; stale events are ignored

At query time · 400M a day

  • Viewport or drawn shape becomes an H3 cover
  • Only boundary cells pay for real geometry
  • "In this school district" is a term filter
  • Price, beds, type, amenities: cheap doc-value filters

Why H3: uniform neighbors, clean parent and child levels, and the same cells drive map clusters and alert matching. S2 or geohash would also work; one system everywhere matters more than which.

Core argument: "Writes are 1M a day. Reads are 400M a day. Every bit of geometry I move from the read path to the write path is paid 400 times less often." H3: Uber's hierarchical hexagonal grid. Res 5 ≈ 250 km² (metro), res 7 ≈ 5 km² (neighborhood), res 9 ≈ 0.1 km² (a few blocks). 64-bit ids, known parent at every coarser level. Map query: (1) client sends viewport or polygon + zoom; (2) server computes the H3 cover at a zoom-appropriate resolution: interior cells go into a terms filter on h3_r7/r9, boundary cells into a clause with an exact geo_polygon/bounding-box check, so only a thin ring pays for geometry (the picture: blue interior, orange ring); (3) add price, beds, type, amenities filters on doc values, all cacheable in Lucene. School districts: ~13,000 US districts plus attendance zones. Point-in-polygon per query would be the single most expensive thing we could do. Compute once at ingest in PostGIS (AlloyDB); yearly boundary changes trigger a batch re-tag that emits events. BigQuery GIS is for analytics (market heatmaps, AVM features like distance to transit), never the request path. Versioned indexing: external version = listing version; older versions are rejected. Refresh 1–2 s. "Why not geo_shape everywhere?" It works, and I use it on the boundary. Using it for everything makes every query pay for geometry and hurts caching. Radius search: the circle becomes an H3 cover with exact distance checks on the boundary ring.

Route by geography

A metro query hits one shard, not eight. Shards are balanced by traffic, not area: New York and LA get their own.

Capacity

40k QPS ÷ ~1,500 per node ≈ 27 nodes at peak, about half off-season. Ignores the cache, so it's conservative.

Reindex safely

Blue/green behind an alias. The hot index rebuilds from AlloyDB in under an hour; rollback is one alias swap.

Say: "The most useful fact in this design is that the searchable set is small: 5M active listings, 20 GB. So I split it from the 200M-property index and treat the two completely differently." Hot index: small shards (~2.5 GB) are fast to move, recover and replicate. Custom routing key = metro group (bin-packed H3 res-3/4 cells). A metro viewport hits one shard; a boundary viewport hits two; country zoom returns precomputed cluster rollups. With fan-out, p95 is driven by the slowest shard; one shard per query also multiplies throughput. Hot spots: shards balanced by query traffic, not geography or doc count. Dense metros get their own shard; rural states share. Rebalancing = new routing map, reindex into a new index behind the alias. Warm index: 200M docs on SSD-backed nodes; lower traffic (address search, "what's my home worth", off-market). Snapshots to GCS; if it's down, those features degrade to AlloyDB lookups. Runs on GKE: OpenSearch is the one stateful thing we run ourselves, because geo + ranking is the product. Elastic Cloud is the buy fallback with the same query model. ~1,500 QPS per 16-vCPU node is a planning estimate to validate with a load test. Applied to the full 40k ignoring the ~40% cache hit rate, so conservative. Indexing: ~12 updates/s, a few hundred in bursts, nightly AVM refreshes via bulk API off-peak. "Why not one index filtered on status?" The hot working set becomes 400 GB, not 20, it doesn't fit in memory everywhere, and every query skips 195M irrelevant docs.

Tile-snapped requests

The viewport snaps to map tiles, filters are hashed into the key, the CDN keeps tiles 30–60 s, and a pan reuses its neighbors.

Clusters from cells

A grid aggregation on the stored H3 field, or per-cell rollups kept current by the event stream for the default view.

Render on the GPU

A WebGL map draws thousands of pins at 60 fps. Card details load on hover, not with the pins.

Budget: a tile cache hit is ~40 ms end to end; a miss is ~150 ms on the server plus ~100 ms to draw.

Say: "300 ms for 1,000 pins is mostly a payload and rendering problem, not a query problem." Payload: id (4–8 B), lat/lng as int32 each (8 B), price in thousands (2 B), status byte ≈ 16–20 B. 1,500 pins ≈ 24–30 KB, smaller gzipped or as protobuf. Full JSON cards would be ~1 KB each, 1.5 MB, which blows the budget on mobile. Clustering: nobody can see 40,000 pins in LA. Return clusters from an H3 grid aggregation (OpenSearch geohex_grid/geotile_grid) on the stored cells. For the unfiltered default view, per-cell rollups (count, median price) maintained by a stream consumer are basically static tiles on the CDN. Tile snapping: two users looking at Austin with "3+ beds under $600k" share cache entries; a pan fetches only new tiles. 30–60 s TTL is fine for pins; the detail page is always current. Rendering: Mapbox GL / MapLibre WebGL handles thousands of symbols; DOM markers don't. Base map vector tiles from the vendor. Miss budget: edge 15 + server ~120 + transfer ~20 + render ~100 ≈ 255–300 ms worst case at p95. "What if a user wants 10,000 pins?" Cap at ~2,000 per request and switch to clusters; at that density a sorted list view is the better product answer.

Search deep dive · Ranking and recommendations

Cheap filters first, then a light personal re-rank

1 · Retrieve

OpenSearch

Filters and geo cells, then a default score: freshness, photo quality, completeness, recent price cut. Keep the top 500.

2 · Re-rank

Small model, 20 ms

Gradient-boosted trees on the top 200 with feature-store inputs: price band, homes viewed, engagement. Past deadline, skip it.

3 · Recommend

Same index

"Homes like this": vector search on listing embeddings within the same metro. "For you": daily candidates, refreshed by events.

Fair housing guardrail

No protected-class or proxy features in ranking or recommendations. Disparate-impact checks on every model release. Sponsored results are labeled.

Say: "Most property search is filtering; relevance in the web-search sense matters less. So retrieval is filters plus a simple quality score, and personalization is a small, optional second stage." Default score: recency (new listings first matters to buyers), photo count/quality, completeness, recent price reductions, with decay. A function_score; no ML needed. Re-rank: LightGBM-style model over ~200 candidates, ~50 features precomputed in the feature store (Valkey-backed online store). Under 20 ms on CPU, under a deadline; on timeout, retrieval order. Explicit sorts (price, newest) bypass it. Recommendations: "similar homes" via listing embeddings (features + photos + text) in an OpenSearch k-NN field, always with a geo filter. "For you" candidates generated offline daily, refreshed on save/favorite/view. Saved searches use the same query DSL, so alerts and search agree on what "matches" means. Fair housing (likely to come up): the Fair Housing Act prohibits steering. No race, religion, national origin, familial status, etc., or proxies (neighborhood demographic mix). Legal reviews the feature list; each release runs disparate-impact tests across geography. Evaluation: offline NDCG on saves/contacts, then A/B on contact-agent rate (the revenue event) with latency guardrails.

Search deep dive · Failure modes

What breaks first, and what we do about it

RiskGuard
One metro gets hotShards balanced by traffic; extra replicas for hot shard groups; caches absorb repeats

Region lossPromote the AlloyDB secondary and the warm search standby; CDN serves stale meanwhile

The trade-off I'm making on purpose: search is eventually consistent by a few seconds. Anything that costs money or creates a lead reads the source of truth.

Say: "Here's what I'd expect to page us, in rough order of likelihood." Hot metro: replicas for one shard group are quick to add because the index is tiny; a viral listing is mostly a CDN problem. Expensive queries: simplify polygons server-side (~100 vertices), search_after instead of from/size, cap ~2,000 results, per-query timeouts. Also bots and scrapers: rate limiting and bot detection at the edge protect capacity. Index lag: search keeps working with slightly stale data; alert on consumer lag and end-to-end freshness. The detail page reads the golden record (short-TTL cache with event-driven purge), so the price and status clicked are current. Bad deploys: schema/analyzer changes always go to a new index; mirror a slice of production queries and compare before the alias swap. Node/zone/region: standard. Serving is multi-zone in one region. For a region loss, the DR region has an AlloyDB cross-region secondary (promote in minutes) and a small warm OpenSearch standby fed from Pub/Sub; the 20 GB hot index makes that standby cheap. The CDN serves stale pages and tiles during the switch. Consistency: search results can be seconds stale; browsing tolerates it. Contacting an agent, mortgage pre-approval and saved preferences go to strongly consistent stores. A deliberate CAP choice: for search, availability and latency.

Scaling section: cost optimization, about 6 minutes, three slides. Say: "Structured data is cheap here: 2 TB of golden records and tens of TB of history are rounding errors. Rule: "Buy what is stateful, painful to run and speaks an open protocol. Build what differentiates: ranking and valuation. And name the trigger that would make me switch." Cache, the build vs buy example: - Chosen: Memorystore for Valkey. Valkey is the BSD fork of Redis under the Linux Foundation. Google runs failover with replicas at 99.99%; we pay a managed premium. - Speed doesn't decide: ~50–100 GB hot set at a few hundred k ops/s. A small Valkey cluster handles it. - Why not Dragonfly (self-host on GKE): its edge is multi-threading, one big node replaces a sharded cluster, no fork on snapshot. At our size that saves a handful of nodes, not a fleet, and failover, upgrades, backups and the pager become ours. BSL license, one vendor. - Why not Redis (Redis Cloud or Memorystore for Redis Cluster): Redis left BSD in 2024 (RSAL/SSPL, AGPL added in 2025). Same performance class as Valkey; we don't need Redis Cloud extras (active-active geo, search modules) because search lives in OpenSearch and we write from one region. - Switch trigger: the cache becomes a top-3 cost, or one hot key outgrows a shard. The cache can be rebuilt from AlloyDB, so it is the safest thing to self-host later. OpenSearch: our one stateful build, because relevance and geo are product. Elastic Cloud is the escape hatch. MLS access: some aggregators are owned by competitors (Bridge Interactive is owned by Zillow). Neutral aggregators (MLS Grid, Trestle) where they exist, own RESO Web API/RETS adapters elsewhere, always own normalization. Mortgage: a lead-gen and workflow layer, not a lender. Partner with lenders, an LOS (e.g. ICE Encompass), a pricing engine (e.g. Optimal Blue), credit bureaus. Cost of buying: lock-in and margins. Every vendor behind our own interface.

Scaling · Data and compute

Pay for the shape of the load

BigQuery

  • Baseline slot reservation with autoscaling for ETL and training
  • On-demand for ad hoc (~$6.25 per TiB scanned)
  • Partition by date, cluster by state and H3: scan less
  • Untouched for 90 days: storage drops to about half price

Compute and regions

  • Cloud Run scales to zero for spiky APIs
  • Spot VMs for nightly scoring and reindex
  • Committed use discounts for the AlloyDB and GKE base
  • One serving region + warm DR, not three hot copies

Spring: reads double, writes stay flat. The CUD baseline covers normal weeks, autoscaling on-demand covers the delta, and the cache absorbs ~40% of searches before they reach OpenSearch.

Say: "After photos, the levers are BigQuery and compute, and both come down to paying for the shape of the load." BigQuery slots (I know these well): - Steady, predictable work (the BigQuery subscription loads, nightly ETL, AVM training) runs on an editions reservation: a baseline of slots plus autoscaling to a max, assigned per project so analysts can't starve ETL. - Ad hoc analyst queries run on-demand at ~$6.25/TiB scanned; partitioning by date and clustering by state/H3 keeps scans small. Require partition filters on big tables. - Long-term storage: a table or partition untouched for 90 days drops to about half price automatically. Consider physical (compressed) storage billing for big, compressible tables. - No streaming pipeline to pay for: the Pub/Sub BigQuery subscription writes directly. Compute: - Cloud Run for stateless APIs and ingest workers: per-request billing, scales to zero overnight. - Spot VMs (GCP lists up to ~91% off) for interruptible batch: nightly AVM scoring (200M × ~1 ms ≈ 55 CPU-hours, and only changed homes are re-scored), reindexing, replays. - CUDs (1 or 3 years) for what runs 24/7: AlloyDB, core GKE nodes for OpenSearch. Regions: one serving region, multi-zone, plus a DR region with an AlloyDB secondary and a small warm search standby. Three active regions would triple the hot footprint for reads that a CDN already serves near users. Data locality: listings are US public data; user PII stays in the primary region. Spring peaks as a cost question: reads ~2×, MLS writes flat. Scheduled floors before weekends, autoscaling above them; Feb load test at 2× last year's peak. Degrade cheapest first (longer TTLs, skip re-rank, precomputed values, pause batch); never shed search, listing pages, contact agent, mortgage. Watch: cross-region egress and logging, often a top-five line item. Sampled traces, tiered log retention.
